# 07-04 — One reliable-event stream, replacing three echo hacks

## Why

maze-war currently has three unrelated, ad hoc redundancy mechanisms, each
invented at a different point in this project's history to patch a specific
observed failure, none of them acknowledged:

- `BRICK_DELTA`: echoes `BRICK_ECHO_REPEATS` (2) times after the original,
  queued per-cell, no ACK.
- `RESPAWN`: echoes similarly (`queue_respawn_echo`/`flush_respawn_echo`,
  landed this session, `7c5ae23`) — one slot of pending echo per player slot,
  again no ACK.
- `NAME`: re-broadcast on a blind 1-second rotation regardless of whether it
  was ever lost.
- Backstop for everything: a full `BRICK_FULL` resync every 3 seconds, which
  is the only mechanism with an actual delivery guarantee, at the cost of
  multi-second worst-case latency for the specific cell that got lost.

FujiRealm's `TERRAIN_EDGE` delivery (`server/hybrid_server.py:1340-1441`,
detailed in `07-RESEARCH.md`) is one clean go-back-N mechanism with real
cumulative ACKs, a 0.5s retransmit timer, and a duplicate-ACK fast path that
recovers a single lost frame in well under the timer interval. This plan
generalizes that idea — not the terrain-specific plumbing — into one ordered
reliable-event stream covering `BRICK_DELTA`, `RESPAWN`, and `NAME`, so a
fourth event type in the future is a two-line enqueue call, not a new
repeat-count-and-timer invention.

## Shape

**One ordered stream per client, not one per event type.** Each reliable
thing that happens (a brick breaks at `(x,y)`; slot N enters pending respawn;
slot N's final respawn position; slot N's name changed) is enqueued in the
order it happened, each tagged with a monotonic 16-bit revision number scoped
to that client's stream. This mirrors FujiRealm's single ordered pipeline
(not one pipeline per tile) and means the client only ever needs to report
one number — "I have applied everything through revision R" — to
cumulatively acknowledge an arbitrary mix of event types.

- **Server side**: a small per-client deque of in-flight (unacknowledged)
  reliable events, each `(revision, event_bytes)`, retransmitted
  byte-identical on the same schedule FujiRealm uses: unacked longer than a
  retransmit interval (start with 250-500ms, tune against maze-war's 10Hz
  tick rather than assuming FujiRealm's 0.5s is right for a different tick
  rate) → resend the whole in-flight set oldest-first. A duplicate ACK
  (client reports the same revision it already reported last time, meaning
  the real next one got lost) triggers an immediate retransmit, rate-limited
  to avoid a burst loop, and does **not** count against a retry budget — the
  same "ordinary loss isn't evidence of a dead link" distinction FujiRealm
  makes. Given maze-war's event rate is far lower than FujiRealm's continuous
  terrain streaming, a shallow pipeline (2-3 in flight, or even stop-and-wait
  to start, with pipelining as a later optimization if warranted) is
  reasonable — don't copy FujiRealm's exact depth without checking whether
  maze-war's traffic pattern justifies it.
- **Escalation**: after a small number of retries with no forward progress,
  fall back to whatever full-resync already exists for that data class —
  `BRICK_FULL` for a stuck brick event, a fresh unconditional `RESPAWN`
  broadcast for a stuck respawn, a fresh `NAME` broadcast for a stuck name.
  This is a *per-event-type* fallback, not a single universal one; design it
  that way rather than forcing one generic "resync everything" hammer.
- **Client → server ack**: the existing `DELTA` packet (4 bytes: type, seq,
  pid, joy) has no spare room and already carries legacy compatibility
  formats through the server's normalization layer (`doc/protocol.md`,
  "Compatibility formats accepted by server") — growing it is a wire-format
  risk best avoided. **Add a small dedicated ack packet type** instead
  (client → server, a handful of bytes: type, the client's own seq, the
  highest applied reliable-stream revision), sent whenever a new reliable
  event has just been applied (event-driven, not a fixed timer) so the
  server sees progress as soon as it happens rather than waiting for the next
  scheduled tick.
- **Client side**: apply reliable events strictly in revision order (a gap
  means "wait, don't apply the follower yet" — same principle as maze-war's
  existing snapshot-sequence handling, which already rejects
  out-of-order/stale data). This is a real behavior change from today's
  independent per-type echo handling, so audit each of the three event
  types' current apply-side code (`NET_BRICK_DELTA_APPLY`, `NET_RESP_APPLY`
  path, `NET_NAME_APPLY`) for anything that assumed "apply immediately,
  independent of other event types" that the new in-order constraint would
  change.

## Risks

- **This is a real protocol/behavior change, not a pure addition.** Unlike
  `07-01`-`07-03`, this plan changes *when* a client applies brick/respawn/name
  events (in revision order, all three types interleaved on one stream)
  rather than *whether* it eventually applies them. Test interleavings
  explicitly: a brick break and a respawn happening in the same tick, in both
  possible orders, must apply in the order the server actually enqueued them.
- **Retiring the old mechanisms is itself a change worth measuring
  separately from adding the new one.** Land the new reliable stream
  alongside the old echo mechanisms first (belt and suspenders), confirm it
  actually recovers loss faster/more reliably than the old bursts in a
  controlled test (the `tests/rig/link.py` delay+loss relay from the
  2026-09-09 lag investigation is exactly the right tool for this), *then*
  remove the old mechanisms in a separate, easily-revertible step.
- **The one-stream-per-client design assumes event order matters more than
  event independence.** If a future event type genuinely needs to skip ahead
  of an earlier stuck one (unlikely for maze-war's current event set, but
  worth a sentence of design justification if it comes up), a single ordered
  stream is the wrong shape — flag this rather than silently discovering it
  mid-implementation.

## Acceptance

Against the `tests/rig/link.py` relay at a range of loss rates (reuse the
2026-09-09 lag-investigation rig rather than building a new one), a lost
`BRICK_DELTA`, `RESPAWN`, or `NAME` update is recovered within one
retransmit-timer interval in the overwhelming majority of cases, and within
one fast-retransmit round-trip when the loss is immediately followed by
further traffic (the duplicate-ACK case). No event is ever misapplied
out of order. `tests/respawn_echo_smoke.sh` and `tests/player_names_smoke.sh`
pass against the new mechanism with equivalent or stronger assertions than
today's fixed-repeat-count checks.
