# 07-01 — Server: UDP socket to TCP listen/accept

## Why

FujiRealm's realtime channel runs over TCP; maze-war's runs over UDP. The
underlying netstream handler both projects share treats transport as a runtime
flag with no handler-side difference (`07-RESEARCH.md`), so this plan is scoped
tightly: change how the server accepts and identifies connections, and change
nothing about how it decides what to do with the bytes once they're framed and
decoded. Landing this first, in isolation, means a transport regression can
never be confused with a framing or reliability-mechanism regression in
`07-03`/`07-04`.

## Shape

- Replace the single `SOCK_DGRAM` socket with a `SOCK_STREAM` listening socket
  (`socket()`, `bind()`, `listen()` with a small backlog) plus up to
  `MAX_PLAYERS` accepted client sockets.
- `struct client_slot` gains an `int fd` (the accepted socket; `-1` when the
  slot is free) alongside (or replacing — see below) the existing
  `struct sockaddr_in addr`. Client identity becomes "which fd this data
  arrived on," which is simpler than the current UDP model's
  address-equality lookup (`addr_equal()` across all slots) — a TCP `accept()`
  hands back a distinct fd per connection, no matching needed.
- Extend the server's existing `poll()` loop (`server/main.c:1808-1820`, today
  one `pollfd` for the one UDP socket) to a small array: one entry for the
  listening socket (`POLLIN` → new connection, `accept()` it into the lowest
  free slot using the same slot-allocation rules `find_or_add_client` already
  implements — lowest free non-zombie slot for a new client, slot 0 never
  zombie-filled, etc. — unchanged), plus one entry per in-use client slot.
- Read/write become `recv()`/`send()` on the client's fd rather than
  `recvfrom()`/`sendto()` with a from-address. **TCP has no datagram
  boundaries** — a `recv()` can return a partial frame, multiple frames, or a
  frame split across two calls. The COBS+checksum decoder already assumes a
  byte stream with no message boundaries (that's the whole point of Phase
  5.1's framing work), so this should require no change to the decoder logic
  itself, only to how bytes are handed to it: byte-at-a-time or in whatever
  chunks `recv()` returns, same as the Atari side already does. Double-check
  `process_client_bytes` doesn't assume "one call = one packet" anywhere.
- `CLIENT_TIMEOUT_MS` reap logic: a TCP peer disconnecting cleanly delivers
  `recv() == 0`; an unreachable peer eventually errors the socket out of
  `poll()`. Keep the existing timestamp-based timeout as the primary
  mechanism (it already handles the "peer vanished without a clean close"
  case, which a real SIO-hop dropout looks like from the server's point of
  view), but also reap immediately on a clean `recv() == 0` or a socket error,
  rather than waiting out the timeout for a peer that told you it's leaving.
- `broadcast_packet` and the various per-client sends become a loop over
  in-use fds instead of in-use addresses; no other change.

## Risks

- **Partial-frame reads.** The single biggest behavioral difference from
  UDP. Test explicitly with a client that writes one byte at a time (the
  Atari's own `NS_SendByte` does exactly this) and with a client that writes
  a whole frame in one `send()` call that the server might still only see
  part of on one `recv()`. The framing layer must not assume either.
- **fd exhaustion / accept() backlog.** With only `MAX_PLAYERS` (4) expected
  connections this is not a real capacity concern, but a client that connects
  and never completes its handshake could squat a slot; keep (or add) a short
  handshake timeout distinct from the steady-state `CLIENT_TIMEOUT_MS`.
- **Nagle's algorithm / small-packet latency.** maze-war's packets are tiny
  (4-51 bytes) and frequent (10Hz). TCP_NODELAY should almost certainly be set
  on every accepted socket, or Nagle's coalescing could add tens of
  milliseconds of pointless latency to exactly the kind of small, frequent
  writes this protocol is made of. Set it and verify with a packet-timing
  smoke test, don't assume the default is fine.
- **Existing smoke tests talk UDP directly** (`tests/*.sh` scripts open a raw
  UDP socket and `sendto`/`recvfrom` the server). Every test that talks to the
  server directly needs its Python harness switched to a TCP `connect()` and
  stream `send`/`recv` with the same COBS decode loop it already has. This is
  mechanical but touches most of the test suite — budget real time for it, and
  do it as part of this plan rather than leaving tests broken for later.

## Acceptance

Full smoke suite passes against the TCP server with the same pass/fail
semantics as today (same bugs still caught, no behavior silently loosened to
make a test pass). A manual two-client session (two `nc`/Python TCP clients or
the updated Linux client from `07-02`) shows identical slot assignment,
zombie backfill, and disconnect/reap behavior to the current UDP server.
