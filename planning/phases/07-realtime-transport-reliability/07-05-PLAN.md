# 07-05 — OPTIONAL, NOT RECOMMENDED: client-authoritative local movement

> **Do not execute this plan without an explicit, separate go-ahead from the
> project owner, given after reading `07-RESEARCH.md`'s "Recommendation"
> section.** It is written up because the user's original request
> ("fujirealm style client/server networking") could reasonably be read to
> include this, and a real decision deserves a real writeup rather than a
> silent omission — not because research found a reason to prefer it.
> `07-RESEARCH.md`'s conclusion: this doesn't address the remote-player lag
> that prompted the investigation (FujiRealm doesn't interpolate remote
> players at all — it snaps them, which is a *downgrade* from what
> `REMOTE_FOLLOW` already does), and it walks back the project's own stated
> authority constraint for a benefit (zero-round-trip local movement) the
> user did not report needing ("local movement seems fine").

## What it would mean

FujiRealm's server (`server/game.py:1367-1488`) does not simulate movement
from an input at all. The client computes and reports its own new position as
an already-decided fact; the server's only role is `_player_destination_allowed`
— confirm the reported destination is exactly one legal, walkable, unoccupied
step from the server's last-known position, and either adopt it verbatim or
reject it and set a one-bit correction flag. There is no second, independent
simulation for the client to diverge from, which is why FujiRealm's client
has none of the predicted/authoritative position split, replay-pending-input
queue, or transmit/move phase-lock concerns that maze-war's own `04-01` plan
exists to address.

Adopting this for maze-war's local wizard would mean:

- Retiring `NET_PX_X/Y` vs `LOCX/LOCY` as two independently-arrived-at
  positions for the local player specifically (remote actors and zombies
  would be unaffected — they're already purely server-reported).
- Retiring the pending-input replay ring, the `NET_RECON_P0`/glide-vs-snap
  correction logic, and the `NET_FRAME_DIV`/`MOVCLOK` phase-lock concern
  entirely for local movement, since there would be nothing to reconcile
  against under normal play.
- The server gaining a `_player_destination_allowed`-equivalent: one-step,
  walkable, unoccupied validation against a client-reported destination,
  replacing its current from-scratch simulation of the local player specifically
  (remote/zombie simulation stays exactly as it is today — this is a change to
  how the *local* player's authority works, not a rearchitecture of the whole
  server).
- A `correction_flags`-equivalent added to `SNAPSHOT` (or wherever it fits),
  and client-side handling: accept-and-move-on if unset, else revert to the
  server's position (small divergence: glide back per the existing
  `LOCAL_FOLLOW` pattern; large divergence: hard snap — this part of
  FujiRealm's design already matches what maze-war independently arrived at).

## Why it's not the default recommendation

- **Does not address the reported problem.** The complaint that started this
  investigation was remote-player lag/snapping, not local-movement
  responsiveness. FujiRealm's local-authority model has no bearing on remote
  rendering, and FujiRealm's actual remote-rendering code
  (`netstream_apply_remote_players`, `atari8-client/fujirealm.asm:6977-7052`)
  is a direct snap with no interpolation — worse than maze-war's current
  `REMOTE_FOLLOW`, not better. Copying it would not help and could make
  remote-actor smoothness *worse* if mistakenly extended to remote actors.
- **Departs from a stated project constraint.** `PROJECT.md`: *"Server
  remains authoritative for wizard position and state — client-side smoothing
  must reconcile to server truth."* This plan is the one place in this phase
  that would actually break that sentence, for local movement specifically.
- **Narrower cheat-resistance for movement, not for anything that matters
  competitively.** Combat/hit-resolution/scoring stay server-authoritative in
  both designs — FujiRealm's own combat and quest systems are fully
  server-side despite client-authoritative movement — so this is a smaller
  trade than "the client controls the game" might sound like, but it is a
  real, deliberate trade, and worth naming precisely rather than either
  overstating or hand-waving it.
- **A large amount of already-hardware-verified code would be retired.** The
  prediction/reconciliation/replay machinery this project has spent multiple
  sessions tuning and confirming on real hardware (Phase 2, and the
  `NET_TX_LAST_STICK`/`LOCAL_FOLLOW` fixes referenced in `STATE.md`) would be
  removed rather than built upon. That's not automatically wrong, but it's a
  much bigger and riskier undertaking than `07-01`-`07-04`, for a benefit this
  session's own user report suggests isn't needed.

## If it's greenlit anyway

Treat it as its own phase, sequenced after `07-01`-`07-04` land and are
confirmed on real hardware (a client-authoritative model is easier to reason
about on top of a reliable transport, not instead of one), and scope it to
local-player movement only — remote actors and zombies keep their existing
server-driven, `REMOTE_FOLLOW`-walked representation regardless of what
happens here, since nothing in FujiRealm's design or this research suggests
touching that.
