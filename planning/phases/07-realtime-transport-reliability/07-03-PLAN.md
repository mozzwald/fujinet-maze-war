# 07-03 — Upgrade frame checksum from 1-byte sum to CRC-16/CCITT-FALSE

## Why

maze-war's COBS framing (Phase 5.1) already gives self-synchronization: no
zero byte survives inside an encoded frame, so the next delimiter is always a
frame boundary, and a corrupted frame costs exactly one frame rather than
desyncing the parser. What it does *not* do well is tell corruption apart
from an intact frame reliably — a one-byte additive sum only catches errors
that change the byte-sum mod 256, which misses a meaningful fraction of
realistic bit-flip and byte-swap corruption patterns on a noisy serial link.
FujiRealm's realtime v3 frame uses a real CRC-16/CCITT-FALSE for exactly this
reason (`07-RESEARCH.md`). This is a self-contained, low-risk upgrade: same
frame shape, same COBS delimiter, same resync property, just a better trailer
check.

## Shape

- Replace the additive-sum computation (server encode, all three client
  decoders) with CRC-16/CCITT-FALSE: polynomial `0x1021`, initial value
  `0xFFFF`, computed over every byte of the frame before the trailer,
  trailer becomes 2 bytes (low, high) instead of 1. This is a **wire format
  change** — bump whatever version marker the protocol already exposes (or
  add one if there isn't a clean one) so an old client and a new server (or
  vice versa) fail closed and visibly rather than silently misinterpreting
  frames with the wrong-width trailer.
- 6502 CRC-16 implementation: a table-driven approach (256-entry lookup table,
  ~1KB, one table lookup plus a handful of XOR/shift instructions per byte)
  is the standard low-cost approach and should comfortably fit the VBI's
  per-frame time budget at maze-war's packet sizes (largest frame is 51 bytes,
  `BRICK_FULL`). Confirm against a real timing budget rather than assuming;
  the VBI already does meaningful work per frame (`NET_VACANT_UPDATE`,
  `NET_SCORELBL`, the move loop) and this session's own display-list-page
  lesson (`memory_layout_smoke.sh`) is a reminder that "just add a table"
  isn't free of side effects on a machine this size.
- Server and both Linux clients: a straightforward CRC-16 table or bit-loop
  in C; no meaningful cost concern there.
- Keep the COBS layer completely unchanged — this plan touches only what
  goes into the trailer and how it's checked, not how frames are delimited.

## Risks

- **6502 code/table space.** A 256-entry 16-bit CRC table is 512 bytes if
  stored as two parallel byte tables, more if stored as 256 words unpacked
  differently — budget this against the memory map in
  `planning/phases/04-render-state-separation/04-RESEARCH.md`'s neighbor,
  `tests/memory_layout_smoke.sh`'s constraints (the display-list-must-not-
  cross-a-1K-boundary lesson applies to any code-size change, not just this
  one — rerun that smoke test after adding the table, don't assume it's fine
  because the change feels self-contained).
- **Cross-version compatibility during rollout.** If the server and a client
  disagree about trailer width, frames won't parse at all rather than parsing
  wrong (COBS framing still finds the delimiter; only the trailer
  interpretation is ambiguous) — verify this fails safely (dropped frames,
  clear counters) rather than in some more confusing way, and land server and
  all clients together rather than incrementally.
- **Proving the upgrade actually helps.** A CRC-16 catching more corruption
  than a sum is a textbook fact, but this project's own discipline this
  session has been "measure, don't assert." Write a test that constructs a
  frame corruption the 1-byte sum provably misses (e.g., two byte swaps that
  cancel in a sum but not in a CRC) and confirm the new check catches it
  where the old one wouldn't have.

## Acceptance

`tests/cobs_resync_smoke.sh` and `tests/packet_checksum_smoke.sh` (or their
CRC-16-aware successors) pass, including a case that specifically
distinguishes CRC-16 detection from the old sum's detection. Real-hardware
session (paired with `07-02`'s hardware test) shows the transport counters
this project already tracks (`NET_CK_BAD` and friends) behaving sanely under
real link noise.
