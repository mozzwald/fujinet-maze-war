# 07-02 — Clients: TCP netstream connection

## Why

Paired with `07-01`. The shared netstream handler makes this the smaller half
of the transport swap: `NET_FLAGS` is a runtime argument to `NS_InitNetstream`
(`clients/atari/maze-war.asm:71,1004`), not something compiled into
`NSENGINE.OBX`, so no handler rebuild is needed — see `07-RESEARCH.md` for the
flag-bit table. `NS_SendByte`/`NS_RecvByte` are already single-byte calls
against a byte stream in both UDP and TCP mode, so the COBS+checksum framing
code should not need to change at all.

## Shape

- **Atari client**: change `NET_FLAGS` from `$04` (UDP, ext TX/int RX clock)
  to `$05` (TCP, same clock config, `REGISTER` clear) as the first attempt.
  Everything downstream of `NS_INIT` — `NET_TX_BUILD_*`, the COBS encode/decode,
  `NET_FRAME_DISPATCH` — should be untouched. If `NS_INIT` fails or the
  connection doesn't behave as expected against real FujiNet-PC, try `$07`
  (add `REGISTER`) per the open question in `07-RESEARCH.md` before assuming
  something deeper is wrong.
- Baud rate: keep `NET_BAUD_LO/HI` at the current 57600 initially, so this
  plan isolates the transport change from a baud change. Treat FujiRealm's
  31250 as a separate, later tuning experiment (see `07-RESEARCH.md`, "Open
  questions").
- **Linux clients** (`clients/linux/main.c`, `clients/linux/sdl_main.c`):
  change `socket(AF_INET, SOCK_DGRAM, 0)` to `SOCK_STREAM`, replace the
  `connect()`-then-`sendto()`/`recvfrom()` pattern (both clients already
  `connect()` their UDP socket, so the call site changes are small) with a
  plain stream `send()`/`recv()`, and feed received bytes through the
  existing `cobs_decode_inplace` the same way the byte-stream framing already
  expects. Both clients already carry a COBS decoder for the server-to-client
  direction; verify it doesn't assume one `recv()` = one frame anywhere (it
  shouldn't, since it was written for a framed byte stream, but confirm).
- Update `doc/protocol.md`'s framing section to describe the transport as
  configurable/TCP rather than assuming UDP, and note that client-to-server
  packets are no longer "unchanged: they arrive as UDP datagrams" — that
  sentence becomes wrong and needs replacing with whatever `07-01` actually
  does for inbound framing on the server side.

## Risks

- **Real hardware is the only trustworthy test for this plan.** This
  project's own repeated lesson (Phase 5.1, and the 2026-09-09 lag
  investigation) is that the emulator's netsio path does not reproduce real
  SIO-hop behavior. Emulator testing here can prove the flag change doesn't
  break the bootstrap handshake and that traffic flows at all; it cannot
  prove the transport swap is actually more reliable. Budget a real-hardware
  session before calling this plan done, not just an emulator smoke pass.
- **Reconnect cost.** FujiRealm's own comments note "~2s of baud hunting" for
  a full netstream reconnect cycle. TCP's connection-oriented nature may make
  a dropped-and-restored link behave differently on reconnect than UDP's
  fire-and-forget model did (a stale half-open TCP connection on either end
  could stall a reconnect attempt in ways a UDP "just start sending again"
  approach never could). Test an explicit disconnect/reconnect cycle, not
  just first-connect.
- **`REGISTER` flag uncertainty.** Documented as an open question in
  `07-RESEARCH.md` — don't assume either setting works without testing
  against the actual FujiNet-PC sidecar or hardware.

## Acceptance

An Atari client (emulator first, then real hardware) completes `NS_INIT`
against the `07-01` TCP server, exchanges DELTA/SNAPSHOT traffic
indistinguishably from the current UDP behavior in normal play, and recovers
from a deliberate disconnect (kill and restart the server, or physically
interrupt the link) without requiring a full Atari reset. Both Linux clients
connect and play identically to their current UDP behavior.
