# 06-01 — Freeze and validate the merged TCP baseline

## Model and handoff

Use **`gpt-5.6-terra` with medium reasoning** for existing-suite validation and
evidence collection. If an actual cross-system regression requires diagnosis,
recommend Sol/high for that fix rather than assuming it is routine validation.
Follow [08-MODELS.md](../08-lobby-rounds-polish/08-MODELS.md).

The closing user-facing and saved summaries must recommend **08-01:
`gpt-5.6-terra`, high reasoning** for shared-code and fixed-address memory
reclamation. Make that recommendation conditional while hardware acceptance
is pending, and pause so the user can switch before starting 08-01.

## Purpose

Phase 6 is the release gate for the networking work already merged into
`a8-net-fix`. Complete it before rounds, rooms, AppKeys, or Lobby code changes
the client/server lifecycle. The result becomes the comparison baseline for
Phase 8.

## Current source baseline

- `server/main.c` is a single-room, four-seat, authoritative TCP server.
- `clients/atari/maze-war.asm` uses TCP NetStream (`NET_FLAGS=$05`), COBS,
  CRC-16, prediction/reconciliation, render positions, and the reliable-event
  receive/ACK path.
- `clients/linux/main.c` and `clients/linux/sdl_main.c` use the same framed TCP
  protocol.
- `make test` runs the current smoke suite; `tests/rig/` contains the delay,
  loss, patrol, convergence, and movement probes used during Phase 4.
- User testing already established that two emulated clients are nearly
  flawless and real Atari/FujiNet play is greatly improved, with occasional
  one-to-two-cell remote jumps accepted for the local-server target.

## Work

1. Record the exact executable baseline commit and any dirty planning-only
   changes separately. Include the pending Phase 4 planning closure in the
   next authorized commit; do not assume validation authorizes committing new
   executable changes before the user's hardware approval.
2. Correct stale planning references that still describe Phase 7 as living
   only on `realm-net`; the TCP/CRC/reliable-event work is now merged into
   `a8-net-fix`.
3. Force-rebuild all four runnable targets. Do not trust timestamps left by
   earlier patch operations.
4. Run the full smoke suite twice. Any nondeterministic failure is a Phase 6
   defect to diagnose, not a reason to start Phase 8.
5. Run a deterministic mixed-session scenario with one Atari client, one SDL
   client, and two configured Zombies. Cover:
   - join and authoritative slot assignment;
   - sustained movement and remote observation;
   - move then fire and turn then fire;
   - a human taking a Zombie slot;
   - clean TCP close and unexpected silence/timeout handoff;
   - brick destruction and full-map repair;
   - death, pending respawn, final respawn, and score agreement;
   - reliable NAME, BRICK_DELTA, and RESPAWN progress, plus repeated direct
     SEATS delivery (SEATS is not currently a reliable inner event).
6. Reuse MCP-managed Atari800 + FujiNet-PC for emulator validation. Start the
   game server first, then the managed FujiNet sidecar and Atari session on the
   same allocated NetSIO port. Use bounded waits and collect the Atari screen,
   NetSIO status, and FujiNet logs on failure.
7. Audit the rig's transport before reusing it: old UDP delay/loss relays do
   not validate the current TCP path. Use `tcp_movement_probe.py` and a
   TCP-compatible delay/fragmentation fixture; distinguish serial framed loss
   from TCP delivery semantics. Do not change the accepted Phase 4 policy.
   Record clean-loopback behavior and one representative
   delayed run. Bounded timed remote-sample playback remains deferred unless a
   future cloud-server test justifies reopening it.
8. Stop for the user's real Atari XL/FujiNet checkpoint. Phase 6 closes only
   after the user confirms the mixed session remains at least as good as the
   current baseline.

## Required evidence

- Exact baseline commit and build command.
- Two consecutive full-suite passes.
- Mixed-session packet/seat/score observations.
- Atari800 artifact and boot method, bounded input sequence, visible result,
  FujiNet selection, and NetSIO diagnostics.
- User-reported physical Atari/FujiNet result.

## Stop conditions

- Any regression in movement, firing, brick state, names, HUD markers,
  respawn, or handoff stops Phase 8.
- A test harness that disagrees with itself must be repaired before its result
  is used, following the Phase 4 measurement lesson.
- Do not reinterpret the occasional accepted local-network remote jump as a
  new failure unless it is worse than the recorded baseline.

## Completion

Phase 6 is complete when VALD-01 through VALD-03 are supported by repeatable
test evidence and the user accepts the physical-hardware comparison.
