# 08-11 — Production registration and promotion

## Model and handoff

Use **`gpt-5.6-terra` with medium reasoning**. Release preparation is procedural once lifecycle tests pass; new defects return to their owning step.
Follow [08-MODELS.md](08-MODELS.md) for escalation, testing-based commit
approval, and handoff rules.

When production and hardware acceptance are complete, report that Phase 8 has
no remaining scheduled step. If promotion or testing is pending, say so and
keep this step open; do not invent a next model/task.

## Preconditions

- Phase 6 and plans 08-01 through 08-10 are complete.
- Every required physical Atari/FujiNet checkpoint is accepted by the user.
- Maze War has an officially registered production Lobby game type/AppKey.
- The public TCP host and every configured room port are reachable externally.
- A final public client URL and the tested external boot packaging are selected;
  publishing the artifact belongs to the production action below.
- QA publication, external launch, AppKey, room browser, leave, and repeated
  switch tests are recorded and passing.

## Reviewable preparation

1. Produce the exact production server configuration and Atari build command.
2. Build from a clean tree and record hashes for the XEX/NetStream artifact and
   server binary.
3. Verify embedded host, TCP port range, production Lobby base, registered
   appkey, client URL, and default kill limit from the built artifact/config.
4. Run the full local suite and a final QA lifecycle test with the release
   candidate artifacts.
   Record any QA-versus-production configuration differences explicitly; a QA
   build does not prove production host/appkey bytes. Inspect the production
   artifact and retain its hash without claiming an unperformed live test.
5. Prepare rollback instructions: disable Lobby publishing, remove/mark room
   entries offline, stop new accepts, and return clients to the last known QA
   build without changing AppKey ownership.

## Production action

Production writes/publication are the final step and require the user's
explicit approval of the concrete release candidate and configuration.

After approval:

1. Publish the approved client/boot artifact at its final public URL and verify
   its downloaded hash matches the candidate.
2. Start production room listeners.
3. Enable production Lobby publication.
4. Confirm every room appears exactly once with correct human occupancy and
   `tcp://` endpoint.
5. Launch from the public Lobby on physical FujiNet, complete a round, switch
   rooms, reboot, and confirm the selected room persists.
6. Exercise SIGTERM cleanup and restart once, proving entries disappear/update
   correctly.

## Completion

Archive the artifact hashes, deployment configuration, Lobby observations,
hardware result, and rollback result in the summary. Keep QA build support and
configuration after release.
