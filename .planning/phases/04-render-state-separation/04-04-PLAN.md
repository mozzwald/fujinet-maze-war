# 04-04 — Clear player-missile memory before enabling PM DMA

## Why

Reported from real hardware 2026-09-04 with a screenshot in
`ref/screenshots/IMG_20260904_201638.jpg`: a vertical dotted line runs down the
screen in the local player's column, appearing from the player's row downward
and tracking the player as it moves.

Established by inspection, not guessed:

- `PMAREA .DS $0400` at `$3800` is uninitialised. `.DS` reserves without
  emitting, so on hardware it holds power-up RAM. Emulation zeroes RAM, which is
  why this has never been visible here.
- `ERASMAN` clears only the four *player* pages (`PL0`-`PL3`, `$3C00`-`$3FFF`),
  and only for actors it is called on. Nothing clears `$3800`-`$3BFF`.
- In single-line PM resolution the missile region is `PMBASE+$300` = `$3B00`,
  inside that never-cleared range.
- The game **enables missile DMA**: `LDA #$03 / STA GRACTL` sets bit 0
  (missiles) as well as bit 1 (players). It never writes `HPOSM0`-`HPOSM3` or
  any missile graphics register — verified by grep, there are no such writes
  anywhere in the client.

So missiles are switched on, never positioned, and fed uninitialised memory.

## Shape

Clear the whole PM area before `PMBASE`/`DMACTL`/`GRACTL` are programmed. Then
decide missiles deliberately: the game does not use them, so the simplest
correct answer is to stop enabling them in `GRACTL` (bit 1 only). Do both — the
clear is the robustness fix, dropping the DMA bit is the intent fix.

## Watch out for

- There are two `GRACTL` writes (startup and the resume path after the host
  prompt). Both set `$03`. Change both or the artefact returns on resume.
- The clear has to happen before DMA is enabled, not merely early in `START`;
  ordering is the whole point.

## Done when

- Hardware cold boot shows no vertical dotted artefacts, confirmed by the user.
- The guard test fails if a `GRACTL` enable is ever reordered ahead of the clear.

## Note on the reported behaviour

The report says the dots track the player and appear only below it. Uninitialised
missile data alone would explain static vertical strips, not ones that follow an
actor, so one of two things is true: the missile HPOS happens to sit near the
player, or a second mechanism is also in play (for example PM page bytes below
the sprite surviving because `ERASMAN` runs only on move commits). Clear the
memory first, then re-check on hardware before assuming it is fully explained.
